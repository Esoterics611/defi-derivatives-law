# 22.1 Agent Architecture for Derivatives Practice

!!! info "Section Objectives"
    After completing this section, you will be able to:

    - Define what constitutes an AI legal agent versus a simple prompt-response interaction
    - Distinguish single-agent from multi-agent architectures and select the right approach
    - Design the five-agent derivatives practice stack with appropriate tool access and oversight levels
    - Build an orchestration layer that routes tasks to specialist agents

---

## What Is an AI Legal Agent?

An AI legal agent is more than a chatbot that answers legal questions. It is an autonomous system that:

1. **Receives a task** — e.g., "Review this incoming ISDA confirmation for compliance with our trading authority"
2. **Plans execution steps** — identify document type, extract key terms, compare against authorized parameters, flag exceptions
3. **Uses tools** — accesses document stores, regulatory databases, internal policy files, and communication systems
4. **Produces structured output** — a compliance report, exception list, or escalation notice in a predefined format
5. **Operates within guardrails** — defined scope, mandatory human checkpoints, and error handling protocols

The critical distinction from a simple AI prompt: an agent **takes action across multiple steps** and **uses external tools** to accomplish a defined objective. A prompt produces text. An agent produces outcomes.

## Single-Agent vs. Multi-Agent Architectures

| Dimension | Single-Agent | Multi-Agent |
|-----------|-------------|-------------|
| **Complexity** | One model handles entire task | Specialized models for each subtask |
| **Context window** | Everything in one context — risk of overflow | Each agent gets focused context |
| **Error isolation** | One error can contaminate entire output | Errors contained within agent boundary |
| **Latency** | Single pass — fast for simple tasks | Multiple handoffs — slower but more reliable |
| **Cost** | Lower token usage | Higher token usage, but better accuracy |
| **Best for** | Simple analysis, single-document review | Complex workflows, multi-document tasks |
| **Derivatives example** | Summarize one CFTC order | Full enforcement response pipeline |

**When to use single-agent**: The task fits within one context window, requires no external tool access, and produces one output type. Example: summarizing a proposed rule.

**When to use multi-agent**: The task involves multiple documents, requires different types of analysis, produces multiple outputs, or must meet quality thresholds that demand independent verification. Example: counterparty onboarding with KYC, legal analysis, document drafting, and compliance sign-off.

## The Derivatives Practice Agent Stack

A comprehensive AI-augmented derivatives practice requires five agent types, each with distinct capabilities:

### 1. Document Intake Agent

**Function**: Parses incoming ISDA documents, confirmations, regulatory filings, and enforcement orders into structured data.

- **Input**: Raw PDF/document files — ISDA Schedules, CSAs, trade confirmations, CFTC orders, Federal Register entries
- **Output**: Structured JSON with extracted fields — elections, thresholds, dates, parties, obligations
- **Tools required**: Document parser (PDF extraction), template library (ISDA field mappings), internal document store
- **Human oversight**: Low for standard documents; High for novel or non-standard formats

### 2. Analysis Agent

**Function**: Performs legal analysis, regulatory classification, and risk assessment on structured data.

- **Input**: Structured data from Intake Agent — extracted terms, protocol specifications, transaction parameters
- **Output**: Legal analysis memos, regulatory classification reports, risk assessments with confidence scores
- **Tools required**: Regulatory database (CEA, CFTC rules, enforcement precedents), internal policy files, risk models
- **Human oversight**: Medium for routine classifications; High for novel fact patterns or ambiguous regulatory status

### 3. Drafting Agent

**Function**: Generates contracts, compliance documents, memoranda, and regulatory filings.

- **Input**: Analysis output plus drafting instructions — document type, audience, required sections, tone
- **Output**: Draft documents in specified format — compliance memos, risk disclosures, Schedule provisions, comment letters
- **Tools required**: Template library, style guide, precedent bank, citation formatter
- **Human oversight**: High for all externally-facing documents; Medium for internal drafts

### 4. Research Agent

**Function**: Monitors and retrieves regulatory developments, case law, enforcement actions, and market intelligence.

- **Input**: Research queries — regulatory topics, entity names, rule citations, date ranges
- **Output**: Research summaries, timeline analyses, comparative tables, regulatory change alerts
- **Tools required**: Web search, CFTC.gov scraper, Federal Register API, legal database access, RSS feed aggregator
- **Human oversight**: Low for monitoring; Medium for research outputs that inform decisions

### 5. Surveillance Agent

**Function**: Monitors on-chain activity and protocol operations for compliance issues.

- **Input**: Blockchain transaction data, protocol state changes, governance proposals, liquidity events
- **Output**: Compliance alerts, position reports, suspicious activity flags, regulatory threshold notifications
- **Tools required**: Blockchain indexer, protocol APIs, position tracking database, alert system
- **Human oversight**: Low for routine monitoring; High for flagged events requiring investigation

### Agent Stack Summary

| Agent | Function | Input | Output | Tools | Human Oversight |
|-------|----------|-------|--------|-------|----------------|
| **Intake** | Document parsing | Raw documents | Structured data | PDF parser, template lib | Low-High |
| **Analysis** | Legal classification & risk | Structured data | Memos, classifications | Reg database, policy files | Medium-High |
| **Drafting** | Document generation | Analysis + instructions | Draft documents | Templates, precedent bank | High |
| **Research** | Regulatory monitoring | Queries, alerts | Summaries, comparisons | Web, CFTC.gov, databases | Low-Medium |
| **Surveillance** | On-chain monitoring | Blockchain data | Alerts, reports | Indexers, protocol APIs | Low-High |

## The Orchestration Layer

The orchestration layer is the "manager agent" that routes incoming tasks to the appropriate specialist. It must:

1. **Classify the incoming task** — Is this a document review? A regulatory alert? A compliance question? An on-chain event?
2. **Select the agent pipeline** — Which agents are needed, in what order?
3. **Manage handoffs** — Pass output from one agent as input to the next, with format validation at each step
4. **Enforce checkpoints** — Insert mandatory human review at defined decision points
5. **Handle failures** — Retry, escalate, or halt when an agent produces low-confidence output

**Architecture flow:**

```
Incoming Task
    → Orchestrator (classifies task type)
        → Intake Agent (if documents involved)
            → Analysis Agent (legal reasoning)
                → Drafting Agent (if output needed)
                → Research Agent (if additional context needed)
        → Surveillance Agent (if on-chain event)
    → Human Review (at mandatory checkpoints)
    → Final Output
```

!!! tip "AI Practitioner Note"
    **Reference architecture for a multi-agent derivatives compliance system using Claude + tool use:**

    Build your orchestrator as a single Claude instance with tool-use capabilities. Define each specialist agent as a separate system prompt + tool configuration. The orchestrator's tools include "call_intake_agent," "call_analysis_agent," etc. Each tool call spawns a new Claude conversation with the specialist's system prompt.

    This approach gives you: (1) clean context separation between agents, (2) the orchestrator's ability to reason about which agent to invoke, (3) structured handoffs via tool input/output schemas, and (4) a single audit trail showing every agent invocation and its result.

    Start with two agents — Intake and Analysis — before building the full stack. Most of the value comes from structured document parsing plus legal classification. Add Drafting and Research when the first two agents are reliable.
